# 本地化与无障碍

## 修改资源之前

找到项目真正的字符串入口：源码字面量、稳定键、提取式目录、翻译平台或包装函数。沿一次真实调用确认回退语言与构建产物，避免只改生成文件。

共享键有多个用途时逐一检查。拆键之后，即使只改中文，其他受影响语言也必须能解析到原来的含义；文件没有变化并不等于回退正确。不要让运行界面出现新键名或意外的外语。

## 不破坏格式契约

- 保留变量名称、参数类型、位置索引及转义。翻译可重排参数，验证身份和类型，不要求原顺序。
- 检查实际使用的复数类别和设备变体。不要通过拼接“数量 + 名词”模拟所有语言。
- 日期、百分比、金额和单位沿用项目的区域化格式器。`0`、缺失值、估算与时间范围要独立表达。
- 译者备注说明变量含义和出现位置；不随手删除备注或把未经审查的翻译标为已完成。

在 macOS 上，修改了旧式 `.strings` / `.stringsdict` 时可用 `plutil -lint -- <实际修改的文件>`；`.xcstrings` 是 JSON，解析后仍需检查键、分支和运行时解析。其他平台使用已有的资源验证器。语法有效不等于语义正确。

## 中文和英文分别成立

中文按钮通常不加句号，完整消息使用正常标点。英文大小写遵循组件和产品已有规范。产品名、用户输入、快捷键及命令不得为了整齐随意改写。不要规定统一的中文字数或“英文一定膨胀多少”的比例。

检查长名字、真实数值、窄窗口和受影响的大字号。优先合理换行、适当空间或真正清楚的紧凑版本；缩小字体、截断对象和不明缩写会把问题留给人。RTL 在范围内时检查混排和方向，伪本地化仅用于布局压力测试。

## 读出的信息也要成立

先查看原生语义，再决定是否需要自定义描述。

| 语义 | 负责什么 | 常见问题 |
| --- | --- | --- |
| 名称 | 控件身份或动作 | 可见“保存”却读成另一个近义词；重复行无法区分对象 |
| 值 | 当前状态或读数 | 未读到被播报为零；数值不带单位 |
| 角色/状态 | 按钮、选中、开关等 | 在文字里再添加系统已播报的“按钮”“已选择” |
| 提示 | 不明显的结果 | 重复名称；只在可关闭的提示里交代删除后果 |

装饰图像不增加无意义的焦点；有信息的图像按任务解释其含义。列表分组、标题层级和焦点顺序应保留视觉上的关系。动态错误可适当公告，但不要让持续变化的读数不断抢话。

改变读出语义后，用辅助功能树或读屏检查名称、值、角色和顺序；如实际做了 VoiceOver/TalkBack 交互，说明所测环境。不要把源代码属性检查说成真人读屏验收。
